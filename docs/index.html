How a WAF treats a browser

Field notes from studying how an F5 anti-bot layer tells a real browser from automation — and the automation-free CDP tooling that made it measurable.

View on GitHub → Read the study
Scope. Everything here was measured from the position of an ordinary visitor, gently and a few requests at a time. Sites, hosts, operators and IPs are intentionally left out. Study anti-bot layers only on systems you own or are authorised to test, and respect each service's terms of use.
01 — Reading the block

A rejection that looks like success

Against an F5 layer, a rejection arrives as an HTTP 200 with an HTML body titled “Request Rejected” — or as a connection reset on the TLS/HTTP layer. The status line tells you nothing; the body does. A scraper that trusts the status code marks a failed fetch as a good one.

Judge a block by the response body, never the status code.

Plain HTTP clients stop working, even with a browser TLS impersonation profile:

ClientResult
HTTP client with a browser TLS profile (chrome / safari / firefox / edge)Request Rejected
HTTP client with no impersonation, plain headersworked one day, connection reset the next
Real browser driven over CDP, no automation flagspage loads, JSON reachable

Passing the browser's cookies to an HTTP client did not help either. The signal is not in the cookies — it is in the client itself.

02 — What actually gets banned

The fingerprint, not the IP

Two findings drove everything else:

finding 01

It was the framework, not the binary

What got flagged was the automation framework's Chrome, not Chrome itself. A real browser driven over CDP, with no automation flags, was treated as a visitor.

finding 02

The device is the identity

The device fingerprint, not the IP, is what gets banned. Time zone, language and WebGL lifted a ban that rotating IPs never did.

finding 03

Everything is time-scoped

A plain client worked one day and was reset the next. A result is a measurement at a moment, not a permanent rule.

03 — The tooling

Measuring it without automation flags

The study ships small, vendor-neutral tools: a Chrome launched like a user would — no chromedriver, no automation flags — and driven only through the DevTools Protocol, plus a one-page diagnostic and a pure block classifier.

# one-page diagnostic: launch, wait for the challenge, print
# the fingerprint the page sees and a verdict
f5-diagnose https://example.com/ --ready-marker "<app-root" --api-path /api/health
f5-diagnose https://example.com/ --fingerprint random --proxy 127.0.0.1:8899
ModuleWhat it is
chrome_cdpChrome over CDP; title read from /json without touching the page; private Xvfb when there is no display; clean shutdown
waf_blockvendor-neutral block detection by body, challenge fast-fail states, BLK-WAF / BLK-RATELIMIT classification
diagnosethe f5-diagnose CLI: fingerprint seen, cookie names, and a verdict
capturediagnostics that never raise: screenshot + HTML, Performance-API resource statuses
This toolkit detects, classifies and fails fast; it does not defeat a WAF.
